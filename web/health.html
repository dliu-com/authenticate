Can visitors use Auth?

The status checker visits like any other guest. It checks that the token page and its sign-in preparation are available, without signing in, generating a token or opening your saved files.

What is checked

  • Token page: visitors can open the page; without it, they cannot start.
  • Page controls: the browser program is available; without it, sign-in and export controls cannot run.
  • Sign-in setup: the public setup is present; without it, the page disables sign-in.
  • Sign-in return page: the popup's return page and program are available; without them, sign-in may not finish.
  • Help pages: visitors can reach the instructions; missing help does not by itself mean token issuance is down.

No application health service

Auth is a static website. It has no application backend or separate health endpoint, and these checks do not add one. Deployment helpers are not a token-processing service.

What a guest cannot test

A guest cannot prove that a particular Microsoft account can sign in, pass MFA or receive API permissions. The checker does not test real token generation, actual token lifetime, clipboard or saved-file operations, or another app's API access.

The configuration check also requires GUID-shaped tenantId, clientId and audience, with clientId equal to audience. Those are public OAuth identifiers, not credentials. Do not log their values. This checks shape, not live Entra consent or assignment.

Timing, caching, safety and optional Microsoft discovery

Run every 15 minutes using dliu-status-bot/1.0 (+https://status.dliu.com/docs). Request sequentially, with a five-second timeout and a 64 KiB limit on GET bodies. Retry a failed check once; mark a function down only after two failed runs. A response taking more than 2000 ms is a warning, not proof of total failure.

Auth responses remain Cache-Control: no-store, max-age=0; CloudFront caching is disabled. Do not add a cached /health route, write probe, load test, bucket listing or authenticated request. HEAD checks avoid repeatedly downloading large scripts and documentation. These six small checks add no backend; the Status app must enforce its overall monthly budget, rather than assuming free account allowances.

Optional upstream discovery: read tenantId from the validated public config, then GET https://login.microsoftonline.com/<tenantId>/v2.0/.well-known/openid-configuration. Allow only that Microsoft host and GUID-shaped tenant value. Expect HTTP 200, application/json, issuer equal to https://login.microsoftonline.com/<tenantId>/v2.0, and an authorization_endpoint on login.microsoftonline.com. This public discovery request uses no Graph call, login or token. It is not part of the six scheduled site checks and does not prove account access or successful token issuance.
