How it works

auth.dliu.com is a small, static page for obtaining a Microsoft-issued API access token. Sign in with an assigned Microsoft account, save or copy the token, then use it in a trusted API tool or agent. Microsoft handles sign-in and token issuance; this site does not run its own authentication broker.

1 token issuerMicrosoft Entra ID, not this website
0 auth backendsStatic files; no token API or session database
Browser-only memoryReusable until a new sign-in, leaving the page or Microsoft expiry

Obtaining a token

One logical API, multiple sites

The existing dliu API Entra registration defines the shared audience and per-site API permissions. It also serves as the browser client with an exact SPA callback at https://auth.dliu.com/redirect.html. No client secret is needed.

A token can work across sites only after each API is configured to trust that same resource and enforce the shared API role and its own scopes. This does not change the sites' ordinary website sign-in or make a token for Microsoft Graph valid for these APIs.

For public availability monitoring without sign-in or tokens, see Health and its full machine-readable reference. Guest monitoring is separate from authenticated API use.

Release builds load shared public OAuth metadata from the central /dliu/entra-tenant-id and /dliu/api-app-id SSM String parameters in eu-west-1. The shared app ID supplies both clientId and audience. These reads happen in the deployment process, not in the visitor's browser or an Auth backend. No token, client secret or AWS credential is published.

Uses Microsoft's authorization-code flow with PKCE and MSAL Browser. Video's managed API has passed live read/write verification. All four managed APIs, including Files, Blog and Trip planner, have passed separately authorised read-only identity checks. This bounded live API verification does not prove every operation or future availability.

Automatic cache-clearing decision

Auth is excluded from the one-day automatic cache-clearing policy. CloudFront uses CACHING_DISABLED, every response has Cache-Control: no-store, max-age=0, and error-cache TTLs are zero. There is no edge-cache retention period to expire, so no scheduled cache-clearing job or one-day cache lifetime is needed. Normal deployments still invalidate /* to publish releases; that is separate from periodic clearing.

The private S3 bucket holds the site's source assets, not an expendable cache or user tokens. Do not apply a one-day S3 object-expiration rule or delete those assets as cache cleanup: the site needs them to remain available. This decision does not change current-page token memory, explicit user exports or Microsoft's token expiry and revocation rules.

No saved token cache

MSAL is configured with memory-only storage and explicit no-cache directives for access, ID and refresh tokens. The SDK cache is cleared immediately after acquisition, including on failure. Only the access token is displayed or exported.

The token stays in the current page's JavaScript memory after saving, copying or switching tabs. Reload, navigation, closing the page, starting another sign-in or Microsoft expiry removes it from this page. It does not save tokens in cookies, local storage, session storage, IndexedDB, a backend or logs. MSAL may use session storage for temporary OAuth transaction metadata. JavaScript memory is not guaranteed to be forensically erased.

Auth's static hosting never receives the generated token. When a trusted client uses it against an application API, API Gateway and the request handler process it for that request, without an application-level user-token cache or persistent token store. Warm Lambda runtimes can retain physical memory until garbage collection; there is no promise of instant forensic erasure when an invocation returns.

Clearing is not revocation. The clipboard may still contain the token, clipboard history may retain it, and an explicitly saved file persists until you remove it. Exported tokens remain valid until Microsoft's expiry. The page cannot clear copies in your files, tools or agents.

Token lifetime and revocation

An app-specific Entra token lifetime policy has been assigned with a target of 23:59:59, just under 24 hours; it is not an organisation-wide default. Actual issued-token lifetime remains unverified. Without an effective custom policy, access tokens commonly last 60-90 minutes. Always use the actual expiry displayed from Microsoft's response; the page cannot extend an existing token.

A copied access token cannot refresh itself. Microsoft may reject future issuance or renewal, but removing an assignment, signing out or clearing this page does not guarantee immediate invalidation of an already-issued bearer token.

What a site compromise means

With no stored credentials or user tokens and no active user browser running the site, control of the static server alone does not let an attacker forge your Microsoft token. But malicious page code can steal a token on your next visit, and an open page may attempt SSO using an existing Microsoft session even without another password prompt.

HTTPS encrypts the connection. It does not prevent XSS, compromised JavaScript or device compromise. Locally bundled scripts, no third-party analytics, a restrictive CSP, no user-generated HTML, no-store responses and explicit clearing/expiry reduce exposure; they do not make an untrusted page safe.

Threat model: an attacker knows the source code

Assume an attacker can read the entire public repository, the bundled browser code, OAuth application identifiers, redirect URLs and API documentation. None of those is a password or signing secret. Knowing them does not let the attacker forge Microsoft's token signature or grant themselves an API role. Security must come from verified tokens and explicit authorization, not hidden source code or undisclosed endpoints.

Assets, actors and trust boundaries

The protected assets are the Microsoft access token, its saved or clipboard exports, the integrity of the token page and its dependencies, the private origin, deployment permissions and the cloud bill. Actors include anonymous visitors, signed-in accounts without API assignment, the assigned API operator, a stolen-token holder and a compromised dependency or publisher. Website sign-in does not grant API assignment.

The browser fetches public static files through CloudFront and its signed S3 origin, then communicates directly with Microsoft for authorization-code/PKCE token issuance. The popup bridge is same-origin with the main page. The access token stays in that page until expiry or cleanup; explicit copy/save moves a separate copy across the browser-to-device boundary. A trusted tool later sends it to the intended API gateway. Microsoft is the token issuer; Auth is a sensitive token-acquisition surface, not a custom issuer or the APIs' final authorization boundary.

Code, history and dependency review: 2026-11-03

The source review covered all 43 tracked files, the eight intentional working diffs and the full local history: one root commit and all 43 local Git blobs. No real credentials, bearer tokens, private keys, private email addresses or private cloud-account identifiers were identified. Gitleaks was unavailable; the equivalent review used manual file inspection and a heuristic scan for key/token/JWT formats, credential URLs, assignments, entropy and identity metadata. This is not a guarantee against arbitrary encoded secrets or remote-only history, forks and artifacts.

The reviewer ran 75 selected existing tests plus 135 additional in-memory MSAL/console cases or check groups, including PKCE/S256, state/nonce rejection, origin topology, bridge cleanup, cache suppression and malformed exports. Separately, the final full build/test run passed 79 registered tests, including infrastructure synthesis and the isolated publication-ignore regression. The extra in-memory groups are not 135 separately registered tests or real cross-browser OAuth transactions.

Both npm audit --omit=dev and the full audit, including development dependencies, reported two moderate affected-package records for the same minimatch advisory: minimatch and its CDK parent. No high or critical advisory was reported. The browser build contains local code and MSAL packages, not CDK, AWS SDK, jose or the retired broker. Registry integrity records were reviewed; fresh provenance comparison against registry tarball bytes was not performed.

The read-only IAM review found only certificate and static-deployment helper functions. S3 access is bucket-scoped; generated ACM/GetChange and CloudFront invalidation permissions include wildcard resources. No anonymous helper-role assumption or invocation path was demonstrated. Narrower helper privileges, logging, rollback/versioning, publisher/CI protection and budgets are operational follow-ups, not fixes silently applied by this review.

What threat-model tests can establish

Use synthetic credentials and isolated browser mocks to test configuration rejection, explicit scope requests, disabled SDK token caching, cache cleanup after failed acquisition, export formats, repeat copying, expiry, navigation and stale-operation handling. Infrastructure checks can assert private-origin access, CSP, disabled edge caching and no-store headers. Negative tests are evidence for those tested boundaries, not proof that every attack is impossible or that live Entra and every application's authorization settings are correct.

The known-source review exercised the installed MSAL implementation's PKCE/S256, state and nonce rejection, popup/bridge restrictions and cleanup, origin lookalikes and malformed credential exports with synthetic data. It found no confirmed exploitable issue or real secret in the reviewed publishable source snapshot. This was a local review, not a live penetration test, a dependency-advisory guarantee or clearance of future edits, remote Git history or other applications.

The dependency-advisory check on 2026-11-03 again reported a moderate denial-of-service advisory in minimatch, bundled by the installed CDK library. This dependency is used by local deployment tooling, not the browser token console. No attacker-controlled glob input was found in the reviewed Auth deployment path. The audit reported no automatic fix; monitor a compatible CDK update rather than treating the dependency audit as completely clean.

Before publishing source

Review every file selected for commit and the Git history for credentials, bearer tokens, private configuration and personal information. Ignore rules do not remove data already tracked or committed. Keep generated configuration and deployment artifacts out of source control, use placeholders in examples, and review dependency changes. If a real secret has been exposed, removing it from the latest file alone is insufficient: revoke or rotate it and address the published history.

See Microsoft's access-token guidance and configurable token lifetimes.

Which apps can use it?

All four apps use the same dliu API user role, but the role never bypasses an operation's permission checks. Website sign-in and sharing remain separate and unchanged. This is not a Microsoft directory-administrator role.

A remote AI cannot automatically open a file on your computer. Use only its approved secret configuration, never paste the token into chat. Access is powerful across the integrated apps, including destructive operations.

If something goes wrong

If Microsoft sign-in cannot finish, check popup blocking and ask the administrator about account assignment or consent. If an app denies access, check its documented address, token expiry and required permissions. New assignments or permissions require a new token; editing a saved file cannot grant access.
